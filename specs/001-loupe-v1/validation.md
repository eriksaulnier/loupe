## Departures from the planning documents

Each is recorded where it applies.

- `go.mod` declares `go 1.25.0`, not `go 1.23`; `golang.org/x/term` is held at v0.45.0 (plan.md Complexity Tracking).
- The review body and each inline comment are limited to 65,536 characters instead of a 256 KiB body (plan.md Complexity Tracking).
- The `lock` refusal says to wait for or stop the holder instead of removing the lock file (contracts/cli.md).
- Labels are restricted to letters, digits, `_`, `.` and `-`, at most 40 characters (contracts/cli.md, data-model.md).
- `list --json` returns its rows under `runs` (contracts/cli.md).
- Branch resolution reads `branch.<name>.merge` and `branch.<name>.remote` before falling back to the origin owner (plan.md Design Notes).
- `--retry-unknown` reconciles again under the retaken lock before overwriting the attempt (plan.md Design Notes).

## Live checks

The Orca handoff (specs/019-pane-hosts FR-022, task T021), walked on 2026-09-21 in the owner's Orca session on a wide screen, every time via `LOUPE_DEMO_HOME=.demo mise run demo -- handoff 'acme/widgets#42' --json` from Claude Code's Bash tool in the agent pane:

- The handoff returned `ok:true`, `host: orca`, with the new terminal's handle as `paneId`. Review opened in the split, the split took focus, and `q` in review closed the pane; the owner confirmed both.
- With the mapping from Orca's CLI guide (`right` → `horizontal`), a `down` request opened to the right, and `orca terminal list --include-visual-layouts` reported the node as `{"type":"pane-split","direction":"vertical"}`: Orca names the divider, not the placement. After the mapping was flipped, a `down` request opened below; the owner confirmed.
- While review was still open in a pane, a second handoff refused `review-open` (specs/017-live-review) and opened nothing.
- The direction was `down` every time, because the controlling terminal is unreadable from Claude Code's Bash tool: `/dev/tty` fails to open with "no such device or address", `COLUMNS` is 0, and stdin, stdout and stderr are pipes. This led to the width rule in specs/019-pane-hosts FR-005 (amended 2026-09-21): the host's width, else the tty, else `right`.
- `right` under the amended rule: after the rule change and a fresh `mise run demo` build, the same handoff from the same agent pane returned `direction: right`, and `orca terminal list --include-visual-layouts` reported the new node as `{"type":"pane-split","direction":"vertical"}`, so review opened beside the agent. The earlier `down` results came from the tty-only rule, and one came from a stale `dist/loupe-demo` run outside `mise run demo`.
- One transient failure: a handoff refused `pane-failed` with `orca switch: terminal_exited` and `details.step: switch`. Orca had created the split pane, but its shell showed an empty prompt and the command was never typed. A rerun succeeded, and the failure was not reproduced. It shows why the skill reruns only on `step: probe`: a pane had already been opened.
- Observed 2026-09-22 in the owner's Orca session (specs/019-pane-hosts FR-024): `LOUPE_DEMO_HOME=.demo mise run demo -- handoff 'acme/widgets#42' --json` from the agent's active tab returned `focused: true` and review opened beside it with the view moved there; the same command sent into a shell in a background tab of another worktree returned `focused: false`, opened review in that tab, and changed no group's active tab, so the owner's view stayed where it was.

- What the automatic triggers do to each other (specs/007-unattended-publish FR-028). FR-028 wanted a live round judged before each further trigger; `opened` and `ready_for_review` shipped in `667e6b9` before that happened, so the first rounds under them are also the first evidence about them. On 2026-09-17 `#12` and `#13` were each opened ready and then labelled within eight seconds, firing an automatic round and a labelled one on the same commit. The concurrency group held both times: on `#13` the labelled round sat queued from 18:07:14 and ran no step before it was cancelled at 18:08:00, and on `#12` the labelled round waited from 18:06:35 until 18:08:08, four seconds after the automatic round was cancelled. What neither pull request showed is the duplicate: a round was cancelled in both cases before a second review could land, and nothing records what cancelled it, so a labelled round has never been left to finish behind an automatic one that published. That it would publish a second review on the same commit is read off the eligibility step, where a label bypasses the already-reviewed gate, and is unfixed in `eriksaulnier/loupe-workflows`.
